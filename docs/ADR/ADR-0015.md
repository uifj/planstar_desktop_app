# ADR-0015: 订单票档、座位、支付与退款状态尚未形成资金闭环

- **状态**: PROPOSED
- **分类**: DEF
- **优先级**: P0
- **影响维度**: 生产功能 / 安全合规
- **日期**: 2026-11-24
- **来源**: 全项目源码审计与静态核验；2026-11-24 在 `legacy-flutter-3.41.9` 分支复核
- **修复 commit**: —

> 仅登记，暂不修复交易逻辑。未完成资金与履约一致性验证前，不应把真实下单视为已接通支付。

## 背景（Context）

1. 移动端真实订单模式绕过 `RemoteTicketOrderRepository`，直接调用 `PlanstarOrderApi.makeOrder`；下单请求体未发送 `ticketCategoryId`。证据：`../flutter_planstar_app/lib/features/order/application/order_confirm_controller.dart:389-396` 及其 `_confirmBody()`、`_makeOrderBody()`。
2. 服务端报价在未指定票档时选择最低价可用档位，可能与用户界面选择及应付金额不一致。证据：`../planstar_kratos_server/planstar_backend/internal/biz/quote.go:140`。
3. 移动端座位图由客户端生成演示数据，锁座仅在当前进程内有效；所选座位单独展示，未作为订单行写入 `TicketOrder.lines`。证据：`../flutter_planstar_app/lib/features/goods/seatmap/seat_selection_providers.dart:113`、`../flutter_planstar_app/lib/features/order/order_confirm_page.dart:54`。
4. 服务端支付记录没有第三方预支付/回调实现，`pay_params` 为占位内容；退款审核只更新数据库状态，没有调用退款渠道。证据：`../planstar_kratos_server/planstar_backend/internal/data/payment.go`、`../planstar_kratos_server/planstar_backend/internal/data/ops.go`。
5. 待审核众筹 pledge 在创建时立即增加筹款总额与支持人数，而非在支付/审核成功后计入。证据：`../planstar_kratos_server/planstar_backend/internal/data/project_write.go`。

## 决策（Decision）

- 暂不修改下单、选座、报价、支付、退款或众筹代码。
- 后续先定义订单快照的权威字段（票档、座位、数量、金额、优惠、币种），保证界面、报价、下单请求和服务端落单使用同一快照。
- 支付渠道回调、幂等、退款结果和 pledge 状态机必须由后端与支付/运营平台协作实现；客户端本地锁座不能作为库存权威。
- 在真实资金链路验收前，明确区分演示模式与真实模式，不用占位支付参数伪装支付成功。

## 后果（Consequences）

- **正面**: 明确资金闭环缺口，避免把数据库状态更新误认为真实支付或退款完成。
- **负面/风险**: 修复范围跨客户端与后端，并依赖外部支付渠道；需要补充对账、幂等和异常补偿设计。
- **中性**: 记录不改变现有订单聚合、接口或数据库结构。

## 验证（Verification）

- 构造同场次多票档、多座位场景，断言报价、确认页、请求体与服务端订单快照的票档 ID、座位和金额完全一致。
- 并发请求同一座位，验证仅一个请求能获得权威锁座结果，并覆盖锁过期与释放。
- 使用支付沙箱覆盖预支付、成功回调、重复回调、超时关闭、部分退款、退款失败与异步到账。
- 覆盖 pledge 待审核、拒绝、支付成功、重复回调，断言仅有效成功状态计入总额与支持人数。
- 增加渠道账单与本地订单/退款的日终对账，差异必须可定位并可重放。
