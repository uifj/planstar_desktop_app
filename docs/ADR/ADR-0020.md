# ADR-0020: macOS 多窗口、覆盖层与 legacy SDK 兼容修复

- **状态**: ACCEPTED（已在当前分支实现并验证）
- **分类**: DEF
- **优先级**: P0
- **影响维度**: 桌面端启动 / 多窗口 / 跨 engine 数据 / 共享布局
- **日期**: 2026-11-25
- **来源**: `legacy-flutter-3.41.9` 分支 macOS 实际构建、测试与运行核验
- **修复 commit**: `e071161`、`5931e61`、`b894454`

> 本记录覆盖当前 macOS 桌面端正常启动、主窗口与子窗口绘制、桌面组件覆盖层及跨 engine 同步所需的兼容修复。保持 Windows 原生实现、端口契约、业务规则与 DataHub JSON 格式不变。

## 背景（Context）

1. 当前分支为 `legacy-flutter-3.41.9`，审计基线 HEAD 为 `d49d813`，使用 Flutter 3.41.9 / Dart 3.11.5。Flutter 3.50.0 SDK 已按用户要求删除。
2. 原 `MainFlutterWindow` 只为主 controller 注册插件；`desktop_multi_window` 子 engine 不继承注册，导致通知、音频等平台能力缺失。
3. Flutter 3.41.9 的部分 macOS 插件使用 Swift Package，而本机 Xcode 27.2 与现有 CocoaPods 工程、Sparkle 集成发生冲突。原部署目标 10.15 也不再被当前工具链接受。
4. Sparkle 2.9.6 源码 tag 不包含 podspec 所需的预编译 framework；早期本机验证曾使用 `/tmp/Sparkle-2.9.6-src` path pod，该机器相关方案不可移植。
5. DebugProfile 与 Release 均启用 App Sandbox，却未声明 `com.apple.security.network.client`，真实网络访问受限。
6. 桌面组件覆盖层替换 `NSWindow.contentView` 后，AppKit 会清空 `contentViewController`，进而释放 `FlutterViewController` 与 engine。运行中出现 `kInvalidArguments`、dead channel 和子窗口无法绘制。
7. 共享按钮主题使用 `Size.fromHeight(44)`，其宽度为 `double.infinity`。`Row` 对非 flex 子项传递无界宽度时，`OutlinedButton` 产生 `BoxConstraints(w=Infinity)` 布局断言并中断主日历首帧；根 RenderView 无待布局任务并不能证明所有子树布局成功。
8. Windows 原有 DataHub 已是进程级原生实现；macOS 此前只能使用本地轮询降级，多个 engine 不能获得与 Windows 相同的实时同步行为。
9. `launch_at_startup` 的 macOS 生成注册表为空，开机自启设置会落入 `MissingPluginException`；Dart 包约定两个 MethodChannel 方法与 `setEnabledValue` 参数。本轮已改为项目自维护的 Pigeon `LaunchAtStartupHostApi`，Windows/Linux 仍保留该包通道。
10. 无边框桌面组件默认不能成为 key window，Flutter TextField 无法获得键盘焦点；子窗口不应抢占主窗口身份。
11. Dock 重新打开应用时，`NSApplicationDelegate` 未恢复已最小化的主窗口；且 `NSWindow` 最小化后 `canBecomeMain` 会暂时为 `false`，仅按该属性过滤会排除待恢复窗口。
12. macOS 壁纸桥此前只返回单屏逻辑尺寸，并把同一张完整虚拟画布直接设给每块屏幕，Retina 与多显示器布局不正确。
13. 对 `window_manager 0.5.2` 的复核表明，Dart `show()` 已包含 `isMinimized → restore`；此前“show 无法恢复最小化窗口”的审计判断不成立，需明确纠正，避免重复实现。
14. 桌面组件实际运行后，卡片外仍被黑色铺满。Flutter 3.41.9 的 `FlutterViewController.view` 默认背景为黑色；仅将 `NSWindow`、Dart `MaterialApp` 与 `Scaffold` 设为透明不足以让 Flutter surface 参与桌面合成，用户因此误认为组件被设成了系统壁纸。
15. 透明修复后，非活动桌面组件首次拖动与日历格子弹窗仍可能无响应。`DesktopOverlayContentView` 继承 `NSView.acceptsFirstMouse(for:) == false`，AppKit 会将首次按下用于激活窗口而不投递 Flutter 指针流；已有 key-window 能力与卡片命中测试不能覆盖该行为。
16. 首次鼠标修复后，桌面组件仍可能完全没有点击反馈。窗口使用 `.desktopWindow`（`-2147483623`），Finder 桌面图标窗口使用 `.desktopIconWindow`（`-2147483603`）且覆盖整个桌面；图标层更高，透明区域仍会截走卡片上的指针事件。可见、首帧完成和 `hitTest` 单测均不能证明 WindowServer 实际命中归属。

## 决策（Decision）

- 每个子 controller 在 `orderFront` 之前完成生成插件注册、应用自定义插件注册、registrar 获取、manager 注册和 multi-window channel 绑定。`orderFront` 会同步启动 engine，因此注册顺序是生命周期不变量。证据：`macos/Runner/MainFlutterWindow.swift`、`packages/desktop_multi_window/macos/desktop_multi_window/Sources/desktop_multi_window/FlutterMultiWindowPlugin.swift`。
- macOS 明确关闭 SPM，统一使用 CocoaPods；Sparkle 固定为 CocoaPods Specs 镜像中的 `2.9.6`，不依赖 `/tmp` 或本机绝对路径。Runner 与 Pods 部署目标统一为 macOS 12.0。
- 保留 App Sandbox，仅为网络访问增加 `com.apple.security.network.client`；Release 不额外扩大权限，DebugProfile 另保留 JIT、network server 与 get-task-allow。
- `FlutterWindow` 与覆盖层 controller 强引用原始 `FlutterViewController`；覆盖层 wrapper 只包装原 Flutter view，关闭或恢复时保留/还原 controller。engine 关闭前调用 `shutDownEngine`，插件析构不再向已死亡 messenger 注册 Pigeon nil handler。
- macOS 增加进程级 `MacDataHubStore`：串行队列、兼容 Windows 的 `{"revision":1,"entries":{...}}` JSON、唯一临时文件原子写入、连续 revision、持久化失败内存回滚和 Pigeon 类型广播。每个 engine 注册独立 host API 与 listener；Dart 监听端按既有契约将空 key 的删除广播视为全量清空，避免其他 engine 保留旧快照。
- Dart fallback DataHub 使用独占文件锁，在锁内重读磁盘并基于磁盘 revision 写入，避免不同 isolate 用旧快照互相覆盖。
- 平台差异集中在 `desktop_platform_config.dart`：Windows 更新源仍为 `windows`、托盘仍为 `.ico`、桌面组件仍在 create 后 show；macOS 更新源为 `macos`、托盘使用已打包 PNG、桌面组件由原生 overlay 自行显示。
- 共享按钮最小尺寸改为 `Size(0, 44)`：只移除无效的无限宽度，不改变高度、颜色、字体、圆角或业务布局。
- 主 engine 注册 `MacLaunchAtStartupPlugin`，通过 Pigeon `LaunchAtStartupHostApi` 提供 `isEnabled` / `setEnabled` 类型化协议；Windows/Linux 继续使用 `launch_at_startup` 包，公共 `AutoStartGateway` 不变。macOS 13+ 使用 `SMAppService.mainApp`，`.requiresApproval` 不冒充已启用；macOS 12 使用 `SMLoginItemSetEnabled`，因旧 API 无可靠状态查询，仅持久化最近一次成功请求。系统写入失败通过 Pigeon 返回 `loginItemFailed`，不静默成功。
- `CustomWindow.canBecomeKey == true`、`canBecomeMain == false`，让无边框 overlay 可接收文本输入而不成为应用主窗口。
- `applicationShouldHandleReopen` 对 `canBecomeMain || isMiniaturized` 的窗口执行 deminiaturize / makeKeyAndOrderFront；恢复函数由 Runner 与 RunnerTests 共用。普通 `show()` 保持依赖 `window_manager` 已有恢复逻辑。
- 壁纸桥按活动显示器并集和最大 backing scale 生成像素画布；对精确匹配文件名与尺寸的生成画布逐屏裁切，再调用 `NSWorkspace.setDesktopImageURL`。任意用户壁纸仍按原文件应用到每块屏幕，不误裁。
- 保留 `DesktopMetrics.x/y` 的逻辑坐标语义；当前壁纸服务只消费像素宽高，不改变公共 Pigeon DTO。
- macOS 覆盖层启用时显式保存并清除 `FlutterViewController.backgroundColor`、FlutterView layer 的 backgroundColor，并将 layer 标记为非不透明；关闭覆盖层时逐项恢复。该修复只作用于 macOS 原生层，不改变 Windows 的 DWM 合成或共享 Dart 页面。
- `DesktopOverlayContentView.acceptsFirstMouse(for:)` 固定返回 `true`，让桌面层级覆盖层在尚未激活时也把卡片内首次按下交给 Flutter；卡片外仍由既有 `hitTest` 穿透，拖动期间仍临时开放整窗命中。不改变共享拖拽、双击或编辑逻辑。
- 覆盖层层级改为 `CGWindowLevelForKey(.desktopIconWindow) + 1`：高于 Finder 全屏桌面图标层，避免透明桌面层截走点击；仍低于 `.normal` 应用窗口，不变成始终置顶的桌面便签。

## 后果（Consequences）

- **正面**: 主窗口、桌面组件、便签与倒数日可在独立 engine 中绘制；覆盖层不再提前销毁 engine；四个 engine 通过原生 DataHub 实时同步。
- **正面**: macOS 主日历恢复完整标题栏与月网格，Windows 原生目录未修改，共享修复以回归测试覆盖。
- **负面/风险**: macOS 多窗口依赖 AppKit controller/view 生命周期，后续修改覆盖层必须保留强引用不变量。
- **负面/风险**: macOS 12 登录项状态是最近成功请求，不是系统登录项实时枚举；macOS 13+ 待批准状态仍需用户在系统设置批准。
- **负面/风险**: 混合 DPI 虚拟画布按最大 backing scale 生成，1× 屏幕接收高分辨率裁图后由 AppKit 缩放；超大虚拟画布仍受既有渲染器 7680×4320 上限约束。
- **负面/风险**: 当前 macOS 主机不能证明 Windows 真机行为；Windows 运行验证仍需 Windows CI 或设备。
- **中性**: 未改业务规则、依赖方向、公共端口契约或存储格式。

- 本地 `packages/desktop_multi_window/windows` 与 `lib` 逐文件对比 pub 缓存中的 `desktop_multi_window 0.3.1` 上游基线，`diff -qr` 均为零差异；仅 macOS 实现为本地适配，Windows 多窗口运行代码与 Dart API 未改变。
- `test/desktop_platform_config_test.dart` 锁定 Windows 更新源、托盘图标、桌面组件显示行为和原生 DataHub 选择；`test/data_hub_test.dart` 对 Windows/macOS 分别验证原生 clear 广播不会在本 engine 保留旧键。
