## 背景（Context）

月历读模型的计算复杂度与可见天数无关，而是随事件历史长度线性放大：

1. **逐日推进不快进**：`RecurrencePolicy.occurrences` 从 `event.startDate` 起
   `cursor.addDays(1)` 逐日推进（recurrence_policy.dart:22/34/46），上限
   `maxDays = 4000`（:19），循环条件每轮调
   `cursor.differenceInDays(hardEnd)`（:36-37），`_matches` 内再调
   `date.differenceInDays(origin)`（:71）。三年前创建的事件要先空算约 1100 次
   `_matches` 才进入可见区间。`monthDataProvider` 对每个事件调一次
   `occurrences(event, range)`（calendar_controllers.dart:428），总成本
   N × 最多 4000 次 `_matches`。
2. **网格天数是固定的**：`rows.clamp(1, 8)` × `columns.clamp(1, 6)` × 7，
   上限 336 天（calendar_math.dart:88-102），常见配置 42–126 天。
   反转循环为「可见日 × 事件」后成本 ≤ 336 × N；N=100 时约 40 万次降到
   1.26 万次（约 30×）。
3. **现成的 `happensOn` 不能直接替换**：`happensOn`（recurrence_policy.dart:52-61）
   在 lib/ 下零调用（test/widget_test.dart:63/67/114/119 有 4 处测试调用），
   且**缺少 `rule.count` 约束**——`occurrences` 有
   `if (rule.count != null && emitted > rule.count!) break`（:41），
   直接替换会让「重复 N 次后停止」的事件超期渲染。
   `recurrenceUntil` 不用担心：`isExcludedOn` 已覆盖
   （calendar_event.dart:126-128，已核实）。
4. **`metaOf` 零缓存且被两层热点调用**：`CalendarMath.metaOf`
   （calendar_math.dart:111-140）每次做 Solar.fromDate + getLunar + getJieQi +
   getFestivals×2 + HolidayUtil.getHoliday + getDayYi + getDayJi + weekNumberOf，
   无任何缓存。调用点：`monthDataProvider` 每可见日一次
   （calendar_controllers.dart:457）；`_matches` 的 legalWorkday 分支每步进一次
   （recurrence_policy.dart:101）——「每个法定工作日」事件一次重算最多做
   4000 次完整农历 + 节假日查询，与第 1 条叠乘。
5. **yi/ji 是死计算**：`CalendarDayMeta.yi/.ji` 全仓（lib/test/packages）仅出现在
   calendar_math.dart:21-22/32-33/126-127/136-137（声明 + 计算 + 赋值），
   无任何读取点；`subtitle()`（:37-46）不用它们。
6. **lunarYearly 循环不变量未外提**：`_matches` 的 lunarYearly 分支每次重算
   `Solar.fromDate(origin.date).getLunar()`（recurrence_policy.dart:97），
   origin 在整个展开过程中不变。

## 决策（Decision）

按以下顺序实施（顺序不可颠倒，第 1 步是第 3 步的正确性前提）：

1. **补 `happensOn` 的 count 语义**。count 约束等价于「日期不得晚于第 count 次
   发生日」。为每个带 count 的事件**一次性**预计算第 count 次发生日作为硬边界
   （从 startDate 推进到 emitted == count 即停，成本以 count 为界），在同一轮
   读模型计算内按事件缓存该边界，`happensOn` 增加边界判定。不引入逐日计数，
   避免反转循环后复杂度回退。
2. **先写对拍测试（能红）**：同一事件同一区间，`occurrences` 结果集 ==
   逐日 `happensOn` 结果集。覆盖 count / until / excludedDates / lunarYearly /
   legalWorkday / 跨年边界。当前 happensOn 缺 count，对拍测试必然先红，
   红因即根因（符合 AGENTS.md §7 先红后修）。
3. **反转 `monthDataProvider` 展开循环**：外层可见日、内层事件，调补齐后的
   `happensOn`。`occurrences` 保留为领域 API（对拍测试与未来导出功能仍用），
   不再是读模型热路径。
4. **`metaOf` 加进程级缓存**：`Map<String, CalendarDayMeta>`，key 含
   `date.key` 与 firstWeekOffset（周序号依赖周起始）。lunar 包农历/节假日表
   是内置静态数据，缓存可进程级常驻；设容量上限（如 4096 条，LRU 淘汰）防
   长期运行膨胀。未来若引入自定义节假日数据源，须按数据版本失效。
5. **删除 `CalendarDayMeta.yi/.ji` 字段与对应 getDayYi/getDayJi 调用**
   （零读取点，零行为风险）。
6. **lunarYearly 不变量外提**：origin 的农历转换在展开前算一次传入。

候选方案取舍：
- 「给 occurrences 加 range.start 快进」：仍保留 O(历史长度) 最坏情形与
  逐日 differenceInDays 开销，收益低于反转循环，弃用。
- 「引入 freezed/缓存框架」：项目已有 ValueObject 与纯函数基础设施，
  一个 Map 即可解决，不新增依赖。

## 后果（Consequences）

- **正面**: 月历重算成本与事件历史长度解耦（约 30× 量级）；legalWorkday
  事件的农历查询从每步进一次降为每日期一次（缓存命中后近零）；
  为 ADR-0006 的 provider 拆分铺路。
- **负面/风险**: count 边界预计算对「count 很大且间隔很短」的事件仍有一次
  有界推进；缓存占用少量内存；happensOn 语义补齐前若误换调用方会造成
  超期渲染（以对拍测试门禁防住）。
- **中性**: happensOn 从死代码变为公开热点 API，对拍测试成为长期契约。

### 实施记录（2026-11-18）

- test/recurrence_parity_test.dart：10 个对拍用例，实施前 5 个 count 用例红
  （红因即 happensOn 缺 count），实施后全绿；根工程 46 测试全绿。
- 新增 `RecurrencePolicy.expansionOf` → `RecurrenceExpansion` 上下文：
  预计算 count 硬边界（第 count 次发生日，例外日计入次数，与 occurrences
  语义一致）与 origin 农历不变量；静态 happensOn 委托上下文保持独立正确。
- monthDataProvider 反转为「可见日 × 事件」；occurrences 保留给
  reminder/search 的区间展开用途。
- metaOf 进程级 LRU 缓存（上限 4096，key=日期|周偏移）；yi/ji 字段与
  getDayYi/getDayJi 调用已删除（settings.showJiYi 开关本无渲染消费方，
  保留设置字段不动，属既有缺口）。
- 调用次数基准以代码结构保证（反转后内层仅 happensOn，无逐日推进）；
  DevTools 耗时对比留待 ADR-0006 一并回填。
- `flutter analyze` 0 error/0 warning（54→53 条 info 均为 material 弃用，
  见 ADR-0009）。
