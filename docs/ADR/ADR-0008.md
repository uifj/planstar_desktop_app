# ADR-0008: 存储终态评估——drift_flutter/共享 SQLite 取代全量 JSON 快照（分阶段，需确认）

- **状态**: PROPOSED（B 暂缓：决策门禁未触发；C 基线已由 ADR-0002 落地）
- **分类**: DEP
- **优先级**: P2
- **影响维度**: 生产功能 / 安全合规
- **日期**: 2026-11-18
- **来源**: 全量审计（docs/arch_optimize.txt P1-2 原生侧放大）+
  drift_flutter 0.3.1 / sqlite3 3.9.1 源码核实 + Flutter 3.50 hooks 生态核实
- **修复 commit**: e641af2

## 背景（Context）

1. **现状存储是「KV 里套全量 JSON 数组」**：DataHub entries map 的每个 value
   是整个 feature 列表的 JSON 字符串；每次写一个条目，原生侧序列化整个
   entries map + `MoveFileExW(MOVEFILE_WRITE_THROUGH)` 写穿盘
   （data_hub_plugin.cpp:247-275）。数据量三年可达千条级，写放大随总量线性增长。
   ADR-0002 的 Dart 侧缓存/增量只消除 Dart 侧放大，原生侧全量快照仍在。
2. **drift_flutter 已声明未接线**（pubspec.yaml:64，AGENTS.md §10 缺口登记）。
   核实解析链：drift_flutter 0.3.1 → drift 2.35.4 + sqlite3 ^3.0.0（lock 3.9.1）。
   **sqlite3 3.x 已迁移到 Dart build hooks（native assets）**，随应用自动编译
   捆绑 SQLite，无需外部构建配置（sqlite3 3.9.1 README:8-9）；
   sqlite3_flutter_libs 0.6.0+eol 与 sqlcipher_flutter_libs 0.7.0+eol 均为
   空壳占位（drift_flutter pubspec 注释明说）。这是 Dart 3.14 / Flutter 3.50
   原生资产生态的直接红利，Windows 构建已有 MSVC 工具链，hooks 编译可行
   （须以实际 build 验证）。
3. **多 engine 约束（关键）**：drift_flutter 的 `shareAcrossIsolates`
   （native.dart:73-129）只共享**同一 engine 内的 isolate**，不覆盖
   desktop_multi_window 的多 engine。但所有 engine 同属一个 Win32 进程
   （cross-engine-sync-analysis.md §3.1），**各 engine 各自打开同一 SQLite
   文件是 SQLite 原生支持的形态**（WAL + busy_timeout 处理并发）。
4. 既有迁移逻辑可复用：data_hub.dart:437-455 已实现旧 shared_preferences.json
   的去前缀迁移。

## 决策（Decision）

**目标态选 B：共享 SQLite 为单一真相源 + 轻量广播通知**；分阶段推进，
当前不实施（P2，且改存储格式按 AGENTS.md §3 须先经用户确认）。

候选方案：

- **A. drift 作各 engine 本地缓存，DataHub JSON 仍为真相源**：
  双真相源，写穿两层，一致性复杂度高于现状，**弃用**。
- **B. 共享 SQLite 取代 entries map（选定目标态）**：
  - 表结构第一阶段镜像现状：`kv(key TEXT PRIMARY KEY, value TEXT)` +
    `meta(revision)`，行级 upsert 取代全量数组重写；后续各 feature 可演进
    为结构化表（events/cells 独立表，勾选 = 单行 UPDATE）。
  - 每个 engine 经 drift 各自连接同一文件（WAL 模式），写冲突由 SQLite
    事务 + busy_timeout 收敛；revision 单调语义在事务内维护。
  - **跨 engine 通知保留轻量广播**（ADR-0007 的 Pigeon 事件流，载荷仅
    key+revision，value 可选），原生 entries map/PersistLocked 退役，
    DataHub 单例退化为通知总线。
  - 迁移：首启读旧 JSON 快照导入 SQLite（复用 :437-455 模式），导入成功
    前保留旧文件只读备份，失败回退旧路径。
- **C. 维持 JSON + ADR-0002 缓存**：零格式风险，作为基线先行落地；
  原生写放大在当前数据量下可接受，**B 的启动条件**是实测出现可感知的
  写盘延迟或数据量显著增长（以 ADR-0002 回填的基准数据为准）。

实施前置（B 启动时）：
1. dev_dependencies 增加 drift_dev + build_runner（当前均未声明，代码生成必需）。
2. 验证 `flutter build windows --debug` 下 sqlite3 hooks 编译链路（MSVC）。
3. 多 engine 并发写回归：两窗口同时勾选不同日/同日，断言无丢失更新、
   revision 单调、广播可达。
4. 迁移与回退测试：旧 JSON → SQLite 导入幂等；导入失败回退旧路径不丢数据。

## 后果（Consequences）

- **正面**: 写放大从 O(总数据量) 降为 O(单行)；获得查询能力（历史/搜索/
  统计不再全量解码）；存储格式向结构化演进，drift 类型安全契约。
- **负面/风险**: 存储格式变更不可逆（须备份+回退预案）；多 engine SQLite
  并发是新的正确性面（WAL  checkpoint、busy 超时策略需实测）；构建链增加
  hooks/codegen 环节；DataHub 已验收语义须逐条映射保留（回滚、revision、
  origin 标识）。
- **中性**: ADR-0007 的 Pigeon 契约在 B 中继续复用（广播载荷瘦身），
  两项改造不互相返工。

## 评估记录（2026-11-19）

经用户确认，**尊重本 ADR 自身决策门禁，B 暂缓实施，不写任何存储代码**：

- **C 基线已落地**：ADR-0002（子项 1–7）已实现 Dart 侧存储缓存 / 批量写 /
  增量 load / Result 组合子，并删除 SharedPreferencesStore（ADR-0002c）。
  当前「KV 里套全量 JSON 数组 + 原生写穿」的原生侧写放大维持现状，作为
  零格式风险基线运行。
- **B 启动门禁未触发**：本 ADR 决策明文「当前不实施」「未确认前保持
  PROPOSED，不写任何代码」；B 的启动条件是「实测出现可感知的写盘延迟或
  数据量显著增长（以 ADR-0002 回填的基准数据为准）」+ 用户确认。当前无
  基准证据表明写放大已可感知，门禁未触发。
- **运行时验证环境阻塞**：B 前置 3「多 engine 并发写回归」需健康的
  overlay 子 engine；本次 ADR-0006 步骤5 验证期间，子 engine Dart isolate
  持续无法启动（8 次启动均 notify count=1，停滞在 bootstrap.dart:89
  runApp 之前，属 ADR-0010 环境类故障）。即便启动 B，该必需回归当前也
  无法取得健康证据。
- **后续启动条件**：待 (a) ADR-0002 基准回填出现可感知写延迟 / 数据量
  显著增长，且 (b) 子 engine 启动环境恢复可做多 engine 并发回归，且
  (c) 用户再次确认启动 B 时，按前置 1–4（drift_dev+build_runner 接线、
  sqlite3 hooks 构建验证、kv/meta 表 + 迁移备份回退、并发写回归）实施。
  在此之前本 ADR 保持 PROPOSED，DataHub JSON 真相源与 ADR-0007 Pigeon
  广播契约不变。
